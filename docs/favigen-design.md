# Favigen library design proposal

One SVG or PNG logo should produce useful browser and home-screen icons with a single plugin option. Favigen should also expose the icon plan, rendered bytes, and final asset information as separate stages. A Vite plugin can cache and publish the assets, while another plugin can use the same records to assemble a PWA manifest.

## Starting point

[Draft PR #16](https://github.com/josh-hemphill/favigen/pull/16) at `b333605` already provides platform tables, an inspectable icon map, PNG and multiplane ICO rendering, per-icon URL rebinding, and HTML and manifest helpers. Its one-shot helper and 33 unit tests provide a compatibility baseline. TypeScript and those tests passed in an isolated checkout. The stock package build failed while loading its TypeScript Rollup config. The draft eagerly starts source decoding, renders the selected set on every `getIcons()` call, and can return a manifest link when files are disabled. The Vite plugin still calls `favicons`. The first implementation work is to package the draft and add an integration fixture against the package tarball. [Draft source](https://github.com/josh-hemphill/favigen/tree/b333605fdbbfe8213ee00e931ab5d9ec92da210e) · [Original plugin issue](https://github.com/josh-hemphill/vite-plugin-favicon/issues/1)

## What one source generates

Use `favicons({ source: './src/logo.svg' })` or the same call with a PNG. With `favicons()`, the adapter looks for exactly one of `assets/logo.svg` and `assets/logo.png`. If neither or both exist, the diagnostic lists the candidates and shows how to choose `source` explicitly. Source paths resolve against the Vite project root. The library accepts a file path or bytes. Both use the `web` profile, the same rendering defaults, and explicit documentation of generated filenames. In the table, asset names are logical names. The build tool may add a content hash to the output name.

| Profile or mode | Logical asset and format | Sizes or purpose | Discovery |
| --- | --- | --- | --- |
| `web` by default | `favicon.ico`, ICO | 16, 32 and 48 px square planes | Explicit `rel=icon`. Publish the compatibility filename at build root. |
| `web` by default | `favicon-32.png`, `favicon-48.png` | Square PNG with alpha | Sized `rel=icon` tags. The 32 and 48 px files cover ordinary browser use. |
| `web` by default | `apple-touch-icon.png` | 180 px square, opaque PNG | `rel=apple-touch-icon`. |
| `pwa` opt-in, adds to `web` | `icon-192.png`, `icon-512.png` | Square PNG, purpose `any` | Icon records for the manifest owner. |
| `pwa` opt-in, adds to `web` | `icon-maskable-192.png`, `icon-maskable-512.png` | Square opaque PNG, purpose `maskable` | Separate manifest icon entries. |
| Custom targets, opt-in | Caller names PNG canvas outputs and chooses semantic role | Explicit dimensions, including rectangles | Metadata helpers generate tags only for known roles. The caller owns custom discovery. |
| Later vector option | `favicon.svg` for validated vector-safe recipes | Scalable `sizes=any` alongside PNG and ICO | An optional icon tag. Static SVG input works as a source from the first slice. |

The browser profile does not request a manifest. The PWA profile prepares install icons from the same source, and the caller can choose a manifest provider or enable the basic fallback. A site deployed at `/shop/` links to `/shop/favicon.ico`. An origin-wide `/favicon.ico` outside that deployment belongs to the host. Apple documents the touch icon link and separately documents launch images. Chrome's guidance for install promotion calls for 192 and 512 px icons, among other criteria. A site targeting Google Search can opt into a stable square PNG larger than 48 px and link it from its homepage per Search guidance. These variants supply the icons. Installation and offline behavior depend on the app and platform. [HTML icon links](https://html.spec.whatwg.org/multipage/links.html#rel-icon) · [Google Search favicon guidance](https://developers.google.com/search/docs/appearance/favicon-in-search) · [Apple touch and startup images](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) · [Chrome install promotion requirements](https://web.dev/articles/install-criteria#install_criteria) · [Web App Manifest](https://w3c.github.io/manifest/#icons-member)

Small projects usually need few size choices. ICO covers small compatibility sizes, an Apple touch icon covers the main home-screen case, and PWA outputs are opt-in because they solve a different use case. Additional Apple sizes, device-specific launch images, Windows tiles, and Yandex files belong in explicit presets or compatibility helpers. No device table is part of the default browser profile.

## Rendering defaults and escape hatches

**Source intake.** Read local bytes once per source snapshot, detect format from content, and record source dimensions, format, alpha capability, and a digest. Accept static SVG and PNG first, plus JPEG and static WebP once fixtures pass. Normalize orientation before geometry and convert to sRGB with generated metadata stripped. Reject an unreadable path, corrupt or empty file, animation/multipage input, and fully transparent artwork with a diagnostic naming the source and corrective action. Reject unsupported vector features early. Rasterization accepts a documented self-contained SVG subset with a valid viewport or viewBox, local fragment references, and outlined text. Use a parser and structural validation before rasterization. External images, external fonts, scripts, remote resources, nested embedded SVG, and unresolved system-font dependencies produce a diagnostic that suggests outlining, flattening, or exporting PNG. No network access is needed for rendering. Set initial measured ceilings for source bytes, SVG elements, decoded pixels, target dimensions, number of outputs, and concurrent decoded memory. See the release gates for proposed starting limits.

**Geometry.** Apply an optional trim of the fully transparent raster border, then an explicit normalized source crop, then fit and placement, then composite to the output canvas. The crop and fit calculations use the oriented, post-trim source rectangle. A crop is `[left, top, width, height]` in fractions of that rectangle. All fields are finite, positive for width and height, and contained within the source. Merge recipe values from profile to project-wide overrides to role overrides to target-ID overrides, with each supplied value replacing the previous value. The entry source serves every target unless an override supplies another source. Format and purpose invariants apply after merging. Preserve authored whitespace by default. Trim operates on pixels with alpha exactly zero, conserves partially transparent antialiasing, and never guesses that an opaque solid margin is disposable. SVG authors can set the viewBox or provide an explicit crop. V1 accepts trim only for raster sources. For SVG, normalize the root viewport and viewBox through the declared preserveAspectRatio transform. Apply crop, fit and placement to that viewport in vector coordinates. Rasterize the clipped region directly at each target's effective pixel dimensions using the composed transform and a fixed sampling policy. A 16-unit viewBox can produce 512 crisp pixels without a 16 px intermediate. Version the viewport and sampling algorithm and gate Sharp on a thin-stroke fixture at both 16 and 512 px. If a raster probe is needed to detect empty artwork, keep it separate from render inputs.

- `fit: 'contain'` is the default. Scale uniformly until the full crop fits in the inner area. `fit: 'cover'` scales uniformly until it fills that area and crops the excess. `position: [x, y]` in the inclusive range 0–1 controls placement or the anchor for overflow. The center is `[0.5, 0.5]`. Clip cover overflow at the inner box before compositing, so the padded border retains its own background. Explicit crop is available for off-center marks.
- `padding` is the fraction of the shorter output side applied on each edge, with range 0–0.45. Zero is the default for ordinary favicons and 0.08 is the default for Apple touch. For raster input, round crop min edges down and max edges up. Keep SVG crop coordinates fractional until final sampling. Floor scaled dimensions for contain and ceil for cover, with a minimum of one pixel. Apply the anchor by flooring the product of remaining space and axis position. Reject empty inner boxes and invalid crop coordinates. The output canvas dimensions always match the target.
- Alpha-capable targets default to `background: 'transparent'`. A specified solid sRGB color becomes an opaque matte for both the padding and the source's transparent areas. Opaque targets default to white and require a solid color. Ship transparent or solid backgrounds first and reject partial-alpha matte values with a message describing the accepted options. Supply `background: '#18181b'` to preserve the brand surface or make light artwork visible. Use premultiplied-alpha resampling and composite once to avoid dark fringes. Honor `resample: 'nearest'` at integer and fractional ratios for pixel art. Regular resampling uses a fixed, versioned renderer kernel.
- Maskable targets always use an opaque square. The retained artwork rectangle fits inside the centered circle of radius 40% of the side. Compute its contain scale using the smaller of the normal inner-box limit and `0.8 × side / hypot(cropWidth, cropHeight)`, with rounding that keeps the corners inside the circle. This protects even the corners of a filled square. Maskable targets accept a different source, crop, background, or extra padding. Reject `cover` or off-center maskable overrides in the built-in profile because its guarantee is centered containment. A user with purpose-built artwork can later supply a reviewed, pre-rendered target through a custom recipe. [Maskable icon safe zone](https://w3c.github.io/manifest/#icon-masks)

A 1200×300 wordmark will remain uncut and appear as a 32×8 band in a 32 px icon. A 300×1200 transparent mark will appear as an 8×32 band. A single wordmark cannot reliably become a legible square symbol automatically. If the source crop is wider or taller than 3:1 for an output at or below 48 px, report a single warning per source with a preview and suggest an icon-specific source or an explicit crop. A wide logo with a centered badge can use `variants.favicon.crop: [0.375, 0, 0.25, 1]` to use the middle 300×300 px, while its touch and PWA icons retain the uncut wordmark. For a tall logo with a centered badge, `[0, 0.375, 1, 0.25]` produces the same square choice. PNGs with broad transparent margins can use trim on one role, while a dedicated tiny source or nearest-neighbor resampling helps pixel art. For example, set `variants.favicon.source: './brand-pixel.png'` and `variants.favicon.resample: 'nearest'` together while leaving other roles on `brand.svg`. Warn when sampled raster art must upscale for an output of 180 px or larger and when touch art with visible alpha has low foreground contrast against the chosen matte. The latter is an advisory measured heuristic and needs fixture validation before enabling it by default.

| Common `favicons` capability | Favigen design |
| --- | --- |
| One source, path or bytes, PNG/ICO variants, SVG source | Core path. Props select a profile and optionally a target list. |
| Global and platform-specific offset, background, transparency | Default role recipes plus `padding` and `background` overrides. Standardized `contain`, `cover`, anchor, crop, and optional alpha trim address fit and intentional cropping. |
| Pick a platform, subset, or size | Named roles/profiles, stable IDs, allowlist, and explicit custom target specs. Compatible selection stays in the draft wrapper. |
| Pixel art, per-platform art, maskable art | `resample: 'nearest'` and role-specific source overrides. Maskable recipes also work from the default art. |
| Arrays of candidate sources | Add only after role overrides. Prefer an explicit role source, then SVG, then smallest raster that covers the requested fit at native resolution, then largest available undersized raster. Break ties by input order. Report source choice and any upscale. |
| Output channel flags, rename, path prefix, cache busting | Call individual stages. Store names and URLs outside the pixel recipe. Typed HTML and manifest helpers consume the emitted records. |
| App metadata, shortcuts, related apps and service worker integration | Expose icon entries grouped by role and caller-defined shortcut ID. Manifest providers own app metadata, flows, and offline behavior. The basic helper takes a minimal allowlist. |
| Startup art, older vendor sets, cosmetic effects, arbitrary hooks, dark-mode art | Put device startup tables and old vendor manifests behind compatibility or opt-in recipes. Keep dark-mode SVG or a separate themed icon set as a demand-led follow-up. Prioritize source choice and geometry before effects or arbitrary transforms. |

These mappings borrow practical capabilities from upstream. Existing `favicons` offset percentages and boolean background behavior have platform-dependent meaning. The migration guide shows equivalent geometry on fixtures and flags differences a mechanical alias would hide. [Upstream Favicons options](https://github.com/itgalaxy/favicons#usage)

## Core API and artifact lifecycle

Use an immutable prepared source and plan. Taking a snapshot may read bytes, validate/probe sources and compute digests. The planning stage normalizes targets and reports warnings but performs no resize or encode. A consumer can preview or edit the recipe inputs and replan. Rendering can request any target independently. Encoding returns byte metadata alongside the asset so a consumer can emit it or pass it to an emitter. Binding uses the emitted output names and URLs, and can be repeated independently per bundle, HTML document, or deployment.

```ts
type IconSpec = Readonly<{
  id: string
  name: string
  role: 'favicon' | 'touch' | 'app' | 'shortcut' | 'custom'
  group?: string
  mimeType: 'image/png' | 'image/vnd.microsoft.icon' | 'image/svg+xml'
  sizes: readonly { width: number; height: number }[] | 'any'
  purpose?: 'any' | 'maskable' | 'monochrome'
  sourceId: string
  recipeKey: string
}>

type RenderedIcon = IconSpec & Readonly<{
  byteLength: number
  digest: string
  bytes: Uint8Array
}>

type PublishedIcon = IconSpec & Readonly<{
  byteLength: number
  digest: string
  outputFileName: string
  url: string
}>
```

IDs are semantic and stable through renames, such as `app.any.192`. SHA-256 digests are over actual output bytes. `recipeKey` identifies the pixel or container recipe. Names are relative logical paths. Validate duplicate IDs, ambiguous URL bindings, unsafe output paths, and collisions before publication. Permit two logical IDs to share the same physical asset if the emitter assigns them the same name and digest. Return a new byte array per consumer or keep bytes private behind a copy-returning method. Metadata-only callers normally consume records without buffers. Public records travel in an immutable envelope with `schemaVersion: 1`, a build revision, and `icons`, optionally scoped to a selected profile or manifest group. Hooks receive typed warnings with codes, source and target IDs, and actionable messages.

```ts
const source = await prepareSource('./brand.svg')
const plan = planIcons(source, { profile: 'pwa' })
const rendered = await renderIcons(plan, { ids: plan.ids, cache })
const bindings = await emitter.emit(rendered)
// bindings map stable ID to outputFileName and URL, scoped to this output
const published = bindIcons(rendered, bindings)

const manifest = {
  ...existingAppMetadata,
  icons: manifestIcons(published, {
    manifestUrl: 'https://example.com/shop/meta/app.webmanifest',
    urlStyle: 'relative',
  }),
}
await existingManifestWriter.write(manifest)
```

`renderIcon(plan, id)` returns a single record. The batch method accepts bounded parallelism and per-result progress. It commits a record snapshot only on success. `bindIcons` accepts the records to publish and requires a binding for each. A filtered batch has fewer records and cannot emit references to omitted assets. `iconTags` turns published browser/touch roles into typed HTML descriptors. `manifestIcons` defaults to app roles, groups entries by physical URL, MIME and purpose, keeps stable ordering, and accepts a group selector for shortcut icons. `buildBasicManifest` returns a structured value for serialization. These are pure helpers with no cache or filesystem access. Consider an optional output-directory writer, an HTML serializer, and a source diagnostics/contact-sheet tool once the core contract is stable. Adapters may supply their own writers, caches, and structured logging.

## Incremental rendering and publication

Canonicalize normalized effective inputs into two content-addressed layers. A PNG plane key includes source byte digest, normalization and recipe schema versions, deterministic renderer fingerprint, target dimensions, effective crop and positioning, padding, alpha/composite color, resampling, and encoder settings. Include only knobs that affect the result for that recipe. A container key includes format, encoder version and options, and ordered plane keys. This permits an ICO and standalone PNG to share a plane where the size and recipe match. Stable IDs, logical names, URLs, outputs enabled, app metadata, cache location, and absolute source path are excluded. Native implementation versions, exposed backend features and architecture are part of the renderer fingerprint when they can change bytes. Settings that cannot provide a stable identity are uncached.

Use an in-memory byte-bounded LRU with in-flight promise coalescing and a supplied cache interface. The Vite adapter uses it with a namespaced local disk cache by default, with disable and override controls. Persist validated records and blob digests under full recipe keys. Use same-filesystem temporary writes followed by atomic publish, validate size and digest on read, and treat corruption or unavailable cache as a miss with a concise diagnostic. Never cache failures. Bound disk size and age and prune only Favigen entries. Consider process restarts cold when caching is disabled or entries were evicted. Disk hits survive restarts, including URL, metadata, and output name changes, given matching source, renderer and recipes. Re-read source bytes and hash them across restarts. A cacheable versioned inspection result keyed by source digest can hold orientation, dimensions, alpha bounds, source validity and warnings. Reuse that result on a warm-disk hit where valid. If absent, alpha validation or trim may decode source pixels, while cached recipe hits still do zero resize and encode. Coalesce in-flight keys within one process. Independent processes may duplicate work. Identical valid writes may race under the same key, and each atomic publication remains readable. In a live adapter, share a prepared snapshot and re-read on a watched edit, including atomic replacement and source recreation. Render jobs capture the snapshot, and an older generation may finish cache writes but cannot supersede a newer publication.

| Event | Render and cache | Publication, metadata and cleanup |
| --- | --- | --- |
| Repeated request or unchanged rebuild | Zero resize or encode on hits. Same result across restarts with usable disk cache. | A fresh bundle still emits cached bytes through its own context. In dev, reuse the snapshot and URLs. Tags and manifest entries stay equivalent. |
| ICO and standalone PNG share a plane | Resize and PNG-encode once per identical plane key even with concurrent callers. ICO encoder runs once per missing container. | Emit both requested files. For identical whole assets the emitter may coalesce physical files while keeping both logical records. |
| Crop changes for one 192 px target | Miss only for that recipe and containers that actually include the affected plane. Other variants hit, including the 512 px target if unchanged. | Refresh changed URLs when hashed and retain unrelated entries. The next output excludes the superseded owned asset unless another record references it. |
| Default branding source bytes change | Re-probe and render variants that depend on that source, reusing hits for independently supplied art and any cached recipe. | Publish one complete generation after success. Filename may stay the same for fixed ICO. Refresh HTML and manifest from resulting records. |
| Rename, base/CDN URL, app name, or manifest owner changes | Zero pixel work if effective recipes stay identical. | Rename re-emits bytes under the new name. Base/CDN and app metadata changes rebind or regenerate only affected metadata. Only the active owner publishes its manifest. |
| Variant removed | No pixel work for removed targets. Preserve surviving recipe entries for reuse. | Exclude the old item from the current output and metadata. Dev keeps at most one bounded prior snapshot for in-flight fetches. |
| Bad source edit, then a correction | Remove rejected in-flight result. Good previous bytes remain available. Revalidate after correction and reuse matching keys. | Dev serves its last complete snapshot and reports the error once per broken revision. Initial failure surfaces a diagnostic and injects no dead links. Production fails the build. On recovery replace the complete snapshot, then reload pages. |

Build adapters own emission through the active bundle. Clean builds get exactly the new output set. Incremental writes to a preexisting output directory with cleanup disabled follow bundler policy. Any future standalone writer offering cleanup keeps its own inventory and removes only previously owned paths proven absent from the new set, after success and within its designated output directory. Shared directories or existing user assets never become part of that inventory implicitly.

## Vite and manifest ownership

Keep the adapter in the existing Vite plugin project and expose `plugin.api.favigen` with version `1` and the methods below. Core can run without Vite, and additional adapters can implement the same emit and bind boundary when they have their own integration tests.

```ts
type ViteFavigenApi = {
  version: 1
  getDevIcons(): Promise<IconPublication | undefined>
  resolveBuildIcons(context: {
    getFileName: (referenceId: string) => string
    referrerFile: string
  }): IconPublication
}
```

`IconPublication` is the versioned envelope described above. `referrerFile` is the output-directory-relative HTML or manifest file used for relative-base calculation. Use the current output hook's `getFileName`. The API returns finalized names and URLs for that referrer. Asking for them outside the available output lifecycle produces a diagnostic naming the required hook.

- **Dev.** Resolve the source relative to the configured project root. Watch configured source files using Vite's watcher and register namespaced middleware that serves only published IDs and immutable snapshot URLs under the effective dev base. Include MIME type, byte-length and digest ETag. Fixed compatibility aliases revalidate. Middleware serves in-memory bytes and never resolves request paths to source files. Read and prepare lazily when the first relevant page or API request arrives. Coalesce builds and publish one completed snapshot. Use an async `transformIndexHtml` hook with `order: 'post'` to request the same snapshot as the middleware and return the favicon tags. `getDevIcons()` waits for the first complete attempt and shares its result with HTML and middleware, so an external owner can serve the manifest before any page has requested icons. It yields undefined on initial failure and returns the last complete snapshot while a later render runs or fails. After replacing a valid snapshot, trigger a full page reload. During initial failure the HTML hook omits icon and basic manifest links. A companion applies the same readiness rule to its own link. [Vite plugin and dev server hooks](https://vite.dev/guide/api-plugin#configureserver)
- **Build and watch.** In `buildStart`, register watched sources, render or load from cache, and call `emitFile` once per requested output. Use explicit `fileName` for the compatibility ICO and logical `name` for hashed assets. Each output uses current-build reference IDs and its own `getFileName`, base, and document context. Resolve names in the output phase, then finalize structured tags and records. Start with a post-ordered `generateBundle` hook that updates emitted HTML through an HTML parser after Vite's HTML generation. Insert only owned nodes without rewriting unrelated markup. This lets the adapter see existing links and share final URL logic with manifests. Vite's documented HTML asset token is also an option for icon-only insertion. A synthetic fixture verified final asset names, a companion running before the favicon hook, and both HTML insertion mechanisms on Vite 6.4.6, 7.3.8 and 8.3.8 at subpath, relative and CDN asset bases. The full packaged adapter must pass the release matrix. Use the same tested URL resolver for the hook and public API. Build-watch supersedes stale generations and creates fresh emitter refs even on cache hits. [Vite plugin API](https://vite.dev/guide/api-plugin) · [Rollup asset reference lifecycle](https://rollupjs.org/plugin-development/#this-getfilename) · [Rolldown plugin context](https://rolldown.rs/reference/Interface.PluginContext) · [Vite CSS and HTML asset URLs](https://vite.dev/guide/api-plugin#in-css-or-html)
- **Resolve URLs once per consumer context.** For root or subpath deployment use a root-relative URL. For an explicit CDN base use an absolute URL. For relative Vite base derive the reference from each emitted HTML document and each manifest location separately, using POSIX URL paths and verified collected output names. Keep canonical emitted names available in the record. Preserve path escaping, query parameters and fragments. Cross-origin URLs stay absolute. Provide a synchronous URL resolver override for advanced Vite `renderBuiltUrl` setups and test it independently. URLs requiring a runtime JavaScript value cannot be represented in these static files. [Vite base options](https://vite.dev/guide/build.html#public-base-path)
- **Existing icons.** Default insertion preserves user-authored links and skips an equivalent generated link for the same role and sizes. The `inject: false` switch leaves all HTML insertion to the app while retaining the emitted files and API. A fixed-name collision with a user-owned public asset must surface before emission, with a way to request a different name or disable the target.

Treat the app deployment base and asset base as separate values. A root-relative or relative Vite base can serve both defaults. With a full CDN base, use it for icon assets and require an app base when enabling basic mode. Deploy the basic manifest at `manifest.webmanifest` relative to the app root. Its link and launch URLs use the document origin, and it can refer to absolute icons on the CDN. The adapter does not infer the app origin or app path from the CDN host.

Manifest ownership is explicit. The default `manifest: false` emits neither a file nor a link even with the PWA profile. `manifest: 'basic'` opts into a small fallback that builds the sole manifest and its link from the same bound snapshot. It implies the PWA profile unless the caller explicitly supplies compatible app targets. It takes name and optional short name, start URL, scope, display and colors. Default name uses project metadata or the project directory name. Display defaults to `standalone`. Start URL and scope default to the app root, resolved relative to the manifest location in relative deployments. Validate that both resolve on the app origin and that the launch URL is in scope. A fallback for an app at `https://app.example/shop/` and icons at `https://cdn.example/brand/` publishes the manifest at `/shop/manifest.webmanifest` and uses `/shop/` for its launch URL and scope. A document at `/shop/help/` links to the same app-origin manifest.

A companion claims ownership by exposing `plugin.api.favigenManifest = { version: 1, owner: 'companion-plugin-name' }` on its plugin object. During `configResolved`, reject basic mode plus any claim and reject competing claims for the same Vite app. An existing manifest plugin can work without declaring a claim by leaving Favigen's manifest mode off. In basic mode, check configured public paths before the build, check each HTML document for any authored manifest link before adding a fallback link, and check the active output for an existing fallback filename before emission. Apply equivalent route and HTML checks in dev. Fail with the conflicting path or plugin and show how to turn basic mode off. Third-party plugins that add their own manifest after these checks must either declare ownership or run with Favigen's fallback disabled. Manifest link credentials or extra attributes belong to the owner. The fallback helper ships without service worker, precache, shortcut schema, or manifest merging behavior.

For example, a companion Vite plugin retrieves `plugin.api.favigen` in `configResolved`. Its post-ordered `generateBundle` hook calls `favigen.resolveBuildIcons({ getFileName: id => this.getFileName(id), referrerFile: 'meta/app.webmanifest' })` after Vite's HTML output and passes the returned app records to `manifestIcons` using the URLs already resolved for that file. This pure call uses captured build refs and resolves from that output context, so the companion can run before the favicon plugin's HTML hook. The companion writes `meta/app.webmanifest` and injects its link into the emitted HTML. For site base `/shop/`, a nested page can link to `/shop/meta/app.webmanifest`. An icon at `/shop/assets/icon-192.abcd.png` can be written as `../assets/icon-192.abcd.png` inside that manifest. The same example with relative base gives a link relative to each HTML page and a separate path relative to the manifest. In dev its async manifest middleware and HTML hook share the same `await favigen.getDevIcons()` result. The provider derives manifest entries and publishes its file/link only when a snapshot exists. In tests assert one link in both modes and follow it plus every icon URL. An external manifest does not require Favigen's fallback. [Manifest URL resolution](https://w3c.github.io/manifest/#dfn-image-resource)

## Implementation sequence and acceptance

| Slice | Deliverable and gate |
| --- | --- |
| 0. Package the PR | Replace stale release tooling with a small reproducible build. Publish matching ESM, CJS and declarations using explicit exports. Preserve the draft fixtures and verify imports from an `npm pack` tarball in clean ESM, CJS, TypeScript and minimal Vite consumers. Set the initial package floor to Node 22.12 and exercise Node 22 and 24 in CI, with Node 26 as an additional compatibility job. Gate the new adapter on Vite 7 (Rollup) and 8 (Rolldown), covering their engine requirements and both lifecycle implementations. The Vite 6 fixture is useful evidence for a future backport rather than a launch commitment. Keep the existing library name provisional. npm's unscoped `favigen` points to a different project, so choose a scoped name under a verified ownership before publishing. |
| 1. Browser icons from one source | Ship limits, SVG/PNG probing, typed immutable plans, common rendering options, role-specific artwork for the favicon and touch targets, PNG/ICO encoding and both caches. Use Sharp as the proposed Node backend for SVG+raster input, uniform resampling and maintained distribution, with a small internal boundary for probes and rendering. Keep the ICO encoder separate. Evaluate Sharp install footprint and availability on Linux, macOS and Windows on supported architectures before committing to it. A documented single backend and an actionable unsupported-platform error are preferable to silent changes in pixels. |
| 2. Vite and PWA | Implement dev middleware and the build adapter against packaged core, then PWA/maskable assets, versioned API, manifest ownership, and basic fallback. Keep the PR's `Favigen` class and one-shot helper as a compatibility wrapper while moving reusable logic into the staged core. Preserve draft channel flags and platform names through the wrapper, translate simple options, and ensure file-disabled mode emits no helper-owned manifest links. Migrate the draft's Jimp-typed image hook to recipe overrides or a separate legacy entry point before a public stable contract. Keep unpublished non-Vite entry-point experiments out of the Vite release. Existing users on any earlier adapter release keep its behavior, and future adapters get separate entry points when their normal build and watch flows have fixtures.

For common migration, `ViteFaviconsPlugin({ logo: './logo.svg', favicons: { icons: { appleStartup: false }, appName: 'Shop' } })` becomes `favicons({ source: './logo.svg' })` for the browser profile.
